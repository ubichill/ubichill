# フェディバースログインと認証設定

Mastodon・Misskey のアカウントで Ubichill に登録・ログインできるようにする。SSO での新規登録にはメールもパスワードも要らない。招待から来た人は、所属サーバーで認証し、Ubichill の ID と表示名を決めれば元のワールドや部屋に戻れる。

Ubichill のユーザー ID が、引き続きワールド、作者鍵、プロフィール、フォローの持ち主を表す。外部アカウントはログイン手段として紐づける。連合で使う actor やフォローの規則は [連合の設計](federation.md) を参照。

## 段階

| 段階 | 内容 | 設定の置き場所 |
| --- | --- | --- |
| A（このブランチ） | SSO の登録・ログイン・連携・解除、メールなしユーザー、管理者はメール必須 | 環境変数 |
| B | ログイン画面に並べるサーバーをコントロールパネルで決める、メールアドレスの追加（連携として足す）、ログイン方法の追加・解除でパスワードを求めない | Postgres |
| C | メール送信の差し替え（SMTP）と Bot 保護（[ボット対策](bot-protection.md)。Turnstile と hCaptcha） | Postgres |

A だけで招待からの登録は通る。B・C はログインを止める障害の原因を増やすので、A を本番で使ってから必要な分だけ足す。

ログイン方法は、ユーザーごとに画面で切り替える設定ではない。連携を足すとそのままログイン方法が増える（フェディバースのアカウントは認証して、メールアドレスは届いたコードで確かめて足す）。サーバー全体の有効・無効（`FEDIVERSE_SIGN_IN`・`FEDIVERSE_SIGN_IN_SERVERS`・`REGISTRATION`）は障害時に止める手段なので、環境変数のまま置く。

## 登録・ログイン・連携（A）

1. ログイン画面のメールの欄の下に、Mastodon と Misskey のロゴだけのボタンを 1 つ置く。Mastodon か Misskey かは選ばせず、サーバーから判定する（下の「対応するサーバー」）。
2. ボタンを押すと、ログインに使うサーバーを選ぶ画面になる。よく使われるサーバーが、アイコン・名前・種類のロゴ付きで並ぶ（下の「サーバーの選択」）。押すとそのままそのサーバーの認証画面へ進む。
3. 並んでいないサーバーは「その他のサーバー」でドメインを入れる。打ち終わると（500ms）サーバーを確かめ、アイコンと名前を出す。対応していない・接続できないなどは、その理由を出す。確かめられたら「このサーバーで続ける」で認証画面へ進む。
4. ログインか新規登録かは、ログイン画面のタブで選んだ方を引き継ぐ。どちらでも同じ認証に進む。登録済みかを認証の前に明かさないためである。結果は次のとおり。
   - 連携済み: そのユーザーでログインする。新規登録のタブから来ていたら「登録済みだったのでログインした」と知らせる。
   - 未登録: 外部のユーザー名と表示名から候補を出し、ID と表示名を確定してもらう（既存の一意の規則のまま。重複はその場で直せる）。ログインのタブから来ていたら「まだ登録されていない」と添える。カスタム絵文字の `:name:` は候補から外す。
5. 新規登録では、外部のアカウントのアイコンをプロフィールに取り込む（登録画面にも出す）。
   - 取り込まないもの: サーバーの初期アイコン（Mastodon の `missing.png`・Misskey の identicon）と https でないもの。
   - 取り込み方: `safeFetch`（公開のアドレスだけ・5MB まで・リダイレクトは 2 回まで）で取り、アップロードと同じ処理で作り直してから保存する。
   - 登録を待たせないよう裏で行い、失敗しても登録は止めない。登録済みの人のアイコンは変えない。
6. 完了後は元の招待やワールドに戻る。入室できるかは従来の入室判定で確かめる。戻り先は Ubichill 内の相対 URL に限る（`//`・`/\`・制御文字・外部 URL は `/`）。中断・期限切れ・拒否は理由をログイン画面に出す。「やめる」は登録の途中の状態を消す（共用の端末で、別の人が続きから登録できないように）。

既存ユーザーは「設定 → アカウント → ログイン方法」から外部アカウントを追加する。

- 開始したセッションと同じセッションで戻ってきたときだけ追加する（途中でログインし直したら追加しない）。
- 追加・解除にパスワードの入れ直しは求めない（B）。DB のセッションで確かめ（取り消したログインのクッキーキャッシュでは操作させない）、足した・外したことを連絡先メールに知らせる。
- 追加したら、確認済みの連絡先メールに知らせる。
- 別のユーザーに紐づいた外部アカウントの移し替えや、メール・名前の一致による自動連携は行わない。
- 外部で改名してもログインでき、表示用の名前はログインのたびに更新する。サーバー移転時は、ログインできるうちに移転先のアカウントを追加する。

解除では、ユーザーの行を `FOR UPDATE` で押さえてから、外した後に**今の設定で使える**ログイン手段が残るかを確かめる。行の数ではなく、無効化・許可するサーバーの外・連合の block を除いた手段で数える。同時に複数外しても 1 つ残る。パスワードの行はこの操作では外せない。外した外部アカウントで作ったセッションは消す（外す操作をしている今のセッションは残す）。

### メールなしユーザー

Better Auth 1.7 は `email` を一意の文字列として扱い、`users.email` も `NOT NULL UNIQUE`。SSO で登録したユーザーの `users.email` には、乱数と予約ドメインの内部値（`<乱数>@sso.invalid`）を入れ、`emailVerified` は `false` にする。 [予約ドメインの規定](https://www.rfc-editor.org/rfc/rfc2606.html#section-2)

- 連絡先として使ってよいかは shared の `contactEmailOf` だけで判定する（確認済みで、予約ドメインでないもの）。`sendAccountNotice` はユーザーを受け取り、連絡先が無ければ送らない。`user.email` を直接宛先にしない。
- メール登録では `.invalid` のアドレスを受け付けない。内部値にはパスワードの行が無いので、メールでのログインにも使えない。
- Better Auth の `/get-session` は本人にだけ内部値を返す。画面はメールアドレスを表示していないので、加工はしない。表示するときは `contactEmailOf` を通す。
- メールアドレスの追加（B）: 設定の「ログイン方法」でアドレスとパスワードを入れ、届いたコードで確かめると、内部値を置き換えてパスワードの行を作る。以後はメールアドレスとパスワードでもログインでき、連絡先にもなる（下の「メールアドレスの追加（B）」）。

### 管理者

外部サーバーが乗っ取られたり、ドメインを取り直されたりしても、管理者の権限は渡さない。そのために 2 つの条件を重ねる。

1. **管理者は確認済みのメールを持つユーザーだけ**: 管理者のロールの付与は、相手に確認済みのメールが無ければ断る。管理者の判定（`isAdmin`・コントロールパネルの一覧）でも同じ条件を見る。後からロールを管理者にした場合や、DB に直接入った場合でも、メールの無い人は管理者にならない。公式アカウント（`@ubichill`）は従来どおり管理者（起動時に確認済みのメールで作る）。
2. **管理者の権限はパスワードで確かめたセッションだけ**: 管理者でも、SSO だけで入ったセッションでは管理の API（`requireAdmin`）を断り（`password-required`）、画面にも管理者として出さない。パスワードで本人確認をすると、そのセッションで使える。メールの有無だけでは足りないのは、確認済みのメールを持つ管理者（公式アカウントを含む）も SSO を追加でき、SSO のセッションに管理者の権限がそのまま付いてしまうためである。

### 本人確認とセッション

セッション（`sessions`）に、どう本人を確かめたかを残す。判定は `services/auth/sessionAssurance.ts` の純粋関数で行う。

| 列 | 書くとき | 使い道 |
| --- | --- | --- |
| `password_verified_at` | パスワードでのログイン・パスワード変更（Better Auth のフックで `/sign-in/email`・`/change-password` のときだけ）、本人確認（`POST /api/v1/users/me/reauthenticate`） | 管理者の権限を使えるか、直近の本人確認か |
| `auth_account_id` | SSO でのログイン（`accounts.id`。`ON DELETE CASCADE`） | 外部アカウントを外すと、そのアカウントで作ったセッションも消える |

- **パスワードを持つユーザー**は、アカウントの安全に関わる操作をパスワードで確かめたセッションに限る（`requireStrongSession`）。対象は、公開環境の登録・取り消し、CLI の承認、ほかの端末のログアウト。SSO で入ったセッションでは `password-required` で断る。SSO の乗っ取り（外部サーバーの管理者・ドメインの取り直し）を、乗っ取りが終わっても残る権限（足したログイン方法・API トークン）に変えさせないためである。パスワードの無いユーザーは SSO が唯一の手段なので限らない。
- 「直近」は 10 分以内。パスワードを持つ人はパスワードを確かめた時刻から、持たない人はログインした時刻から数える。アカウントの削除（取り消せない）に求める。SSO で入った直後のセッションでも、パスワードを持つ人なら直近とみなさない。ログイン方法の追加・解除には求めない（B で外した）。
- 公式アカウント（`@ubichill`）には SSO を足せず、結び付いていても SSO では入れない。公式の作者として署名する権限を、外部サーバーに渡さないためである。
- 直近でないとき、パスワードのあるユーザーは設定の欄でパスワードを入れ直す。SSO だけのユーザーは、使える外部アカウントでログインし直す。
- 本人確認の API は 15 分に 10 回まで（ユーザーごと）。
- 移行時は、外部アカウントを持たないユーザーのセッションだけ、`password_verified_at` に `created_at` を入れる（migration 0039）。そのセッションはパスワードでしか作れないためである。外部アカウントを持つユーザーのセッションは SSO で作られたかもしれないので埋めず、管理者の操作の前に 1 回パスワードで本人確認してもらう。本番にはまだ外部アカウントが無いので、本番では全部埋まる。
- 一度でも環境に当てたマイグレーションは書き換えない。プレビューで 0038 を作り直したところ、同じものを当て直そうとして backend が起動できなくなった。

## 対応するサーバー

実際に備えるもので判定する。バージョン文字列は見ない。 [Mastodon の OAuth と権限](https://docs.joinmastodon.org/api/oauth-scopes/) · [Misskey の MiAuth](https://misskey-hub.net/ja/docs/for-developers/api/token/miauth/)

| | Mastodon（4.3 以降） | Misskey 系（Misskey・Sharkey・CherryPick） |
| --- | --- | --- |
| 判定 | OAuth の公開メタデータ（RFC 8414）に `app_registration_endpoint`・`profile` の権限・PKCE S256 がある | nodeinfo の `software.name` が Misskey 系 |
| 方式 | OAuth（認可コード + PKCE S256） | MiAuth |
| クライアント | `POST /api/v1/apps` で認証サーバーと戻り先 URL ごとに 1 回登録し、使い回す | 登録しない（許可の画面に名前とアイコンの URL を渡す） |
| 開始 | 認可の口へ。state を一度だけの鍵にする | `/miauth/<セッション ID>?name&icon&callback&permission=read:account`。セッション ID（32 バイトの乱数）を一度だけの鍵にする |
| 本人の取得 | `GET /api/v1/accounts/verify_credentials` | `POST /api/miauth/<セッション ID>/check`（Misskey はトークンを一度だけ返す。`host` が入っていたら他サーバーの人なので断る） |
| 応答の照合 | サーバーごとに違う戻り先 URL・state・付いていれば `iss` | サーバーごとに違う戻り先 URL・セッション ID |
| トークン | 本人を確認したら `revocation_endpoint` で失効させる | 外の口から失効できないので保存せずに捨てる（Misskey の「連携アプリ」に残る） |

**Misskey で OAuth を使わない理由**: Misskey の OAuth は、同意の途中の状態と認可コードをプロセスのメモリにしか持たない。複数台で動くサーバーでは、同意の送信やトークンの交換が別の台に当たると「Invalid or expired transaction ID」やトークンの 400 になる（[misskey-dev/misskey#13088](https://github.com/misskey-dev/misskey/issues/13088)、未解決）。プレビューで misskey.niri.la が実際にこれで失敗した。1 台で動く mi.youkan.uk では通った。MiAuth は状態を DB に置くので台数によらず動く。さらに、OAuth のメタデータを出さない Misskey（sushi.ski など）でも使える。

共通の条件は次のとおり。

- 認可・トークン・nodeinfo の文書は、認証サーバーと同じ origin の https に限る。失効・登録の口が別の origin を指すなら、その口は使わない。
- Mastodon の state で Misskey の流れを進めさせない（逆も）。state と session を両方付けた応答も受け付けない。
- 戻りの URL（認可コード・セッション ID）はログに出さない。

## サーバーの選択

並べるサーバーは管理者がコントロールパネルの「認証」で決める（`featured_fediverse_servers`。B）。初期値は、下の判定に通ることを 2026-11 に実測した 4 つ（マイグレーション 0041 で入れる）。

- 並べるもの: misskey.io・mstdn.jp・mastodon.social・misskey.niri.la（ほかにも misskey.design・nijimiss.moe・mastodon.cloud が判定に通るが並べない）
- 並べないもの: fedibird.com・pawoo.net・sushi.ski は OAuth のメタデータを出していないので対象外

`FEDIVERSE_SIGN_IN_SERVERS` で使えるサーバーを限っているときは、並べるサーバーのうちその中のものだけを出し、1 つも残らなければ使えるサーバーを並べる（`GET /api/auth/fediverse/options` の `featuredServers`）。

`GET /api/auth/fediverse/lookup?server=<ドメイン>` は、認証の前にサーバーの公開情報だけを返す。

1. ドメインを正規化し、許可するサーバーの外・block は断る。
2. 認証サーバーのメタデータで種類を判定する（ログインと同じ）。対応していなければ理由を返す。
3. 種類ごとの公開 API で、名前とアイコンを取る（取れなければ null で続ける）。
   - Mastodon: `/api/v2/instance`
   - Misskey: `/api/meta`
4. 画像の URL は https だけ返す。画面では、読めなければ種類のロゴにする。

同じサーバーの結果は backend が 5 分覚える（接続できなかった結果は覚えない）。IP ごとに 30 回/分に絞る。並べたサーバーのうち、使えないと分かったもの（未対応・許可外）は画面から外す。接続できないだけのものは押せるまま残す。画像はブラウザーが相手のサーバーから直接読む。

理由のコードが無い失敗（古い backend・中継の不調など）は「通信に失敗しました」ではなく、HTTP の状態を添えて「時間をおいてもう一度」と出す。

## 仕組み（A）

### 外部アカウントのキー

`accounts.providerId = fediverse:<認証サーバーの origin>`、`accounts.accountId = サーバー内のユーザー ID`。ソフトウェアの種類はキーに含めない。判定が揺れたり、サーバーがソフトウェアを乗り換えたりしても、別人にしないためである。`(providerId, accountId)` に一意制約を置く（既存の行は `credential` と user id の組なので重複しない）。

表示用の情報（種類・ユーザー名）は `external_account_profiles`（accounts と 1 対 1）に置き、識別には使わない。Better Auth の表は広げない。

### 認証の途中の状態

短命な値は Postgres の `verifications`（Better Auth の表。Ubichill は Better Auth のメール確認を使っていないので、ほかに書く人はいない）に、種類の前置きと SHA-256 のハッシュを identifier にして置く。Redis は使わない（無い構成でも動かすため）。

| 値 | 期限 | 中身 | 使い方 |
| --- | --- | --- | --- |
| state（Misskey は MiAuth のセッション ID） | 10 分 | サーバーの種類と口、Mastodon の client_id と PKCE verifier、戻り先 URL、ブラウザーの印のハッシュ、操作（sign-in / link）、戻り先、画面の origin、link なら開始時のユーザーとセッション | 応答で `DELETE … RETURNING` により一度だけ取り出す |
| 登録の途中 | 15 分 | 外部アカウントのキー、ユーザー名、表示名、戻り先、ログインを押したか | ID と表示名の確定で使い、ユーザーを作ったら・やめたら消す。ID が重複したら残して直させる |

期限切れの行は、既存の定期掃除（10 分ごと、リースを持つ 1 台）で消す。

ブラウザーには、署名付き・httpOnly・`SameSite=Lax`・`Path=/api/auth/fediverse` のクッキーを 2 つ渡す。

- `fediverse_flow`: 開始したブラウザーの印。他人の認証応答を踏ませてログインさせる攻撃を防ぐ。
- `fediverse_sign_up`: 登録の途中の鍵。

### セッションの発行

流れの判断は `services/auth/fediverse/signIn.ts` に置き、HTTP・DB・乱数・時刻は注入する。HTTP の口は Better Auth のプラグイン（`lib/fediverseSignInPlugin.ts`）にする。

- セッションとクッキーは Better Auth の `createSession` と `setSessionCookie` で発行する。そのため、既存のメールログインとクッキーの形・期限・取り消しが同じになる。
- POST の口は Better Auth の origin 確認を通るので、信頼しない Origin からは開始できない。
- 公開する口は [許可リスト](../../packages/backend/src/lib/authEndpoints.ts) に足す。
  - 固定のパス: `/fediverse/options`・`/fediverse/start`・`/fediverse/sign-up`
  - 末尾がホストの形のもの: `/fediverse/callback/<host>`・`/fediverse/client/<host>`

ホストは小文字の英数字・`.`・`-`・ポートだけ。そのままパスに入れ、エンコードしない（`%3A` にすると照合が崩れる）。

ユーザーと外部アカウントは同じトランザクションで作る。同じ外部アカウントで同時に登録されたら、どの一意制約の違反でも先に外部アカウントの持ち主を確かめ、既にいればその人でログインさせる（二重送信で 2 人にならない）。

### 外部への要求

ドメインは正規化し（IDN は punycode）、公開 HTTPS の接続先に限る。要求はすべて既存の [`safeFetch`](../../packages/backend/src/lib/safeFetch.ts) を `maxRedirects: 0` で使う。`safeFetch` は既定でリダイレクトを 3 回まで追い、POST の本文を次の宛先に送るので、0 を明示する。メタデータの 4xx は「未対応」、接続できなければ「接続できない」として扱う。コード・トークン・verifier はログに出さない。

Mastodon でアプリが無効（トークン交換が 401）なら、保存した登録を消して次回は登録し直す。ただし、相手が同意画面でエラーを出した場合は Ubichill に戻ってこないので、検出できない（既知の制約）。

### 設定（A は環境変数）

| 変数 | 既定 | 意味 |
| --- | --- | --- |
| `FEDIVERSE_SIGN_IN` | `on` | `off` で開始・応答・登録の確定・入力の確認を止める。設定を変える前に始めた認証も、応答と確定の時点で断る。連携の記録は残るので、戻せば同じアカウントで入れる |
| `FEDIVERSE_SIGN_IN_SERVERS` | 空 | 使えるサーバーのホスト（カンマ区切り）。空ならすべて |
| `REGISTRATION` | `open` | `closed` で新規登録を止める（メール登録と SSO の両方）。送信済みの確認コードでの本登録・再送も断る。既存ユーザーのログインと連携はできる |

連合で管理者が `block` にしたドメインは、開始・応答・登録の確定のどの時点でも断る。登録の確定では、「同じ外部アカウントが別の画面で登録済みならその人でログインさせる」分岐より前に、無効化と接続先の許可を確かめる。

開始は相手のサーバーへ要求を送るので、Better Auth のレート制限（本番のみ）で IP ごとに 10 回/分に絞る。登録の確定は 20 回/分。

### 信頼の前提と残る穴

- 外部サーバーの管理者は、そのサーバーの誰にでもなりすませる。信頼できるサーバーに限りたい運用では `FEDIVERSE_SIGN_IN_SERVERS` を使う。
- ドメインが失効し、別人に取り直されると、同じ origin と ID で既存のユーザーとしてログインできうる。完全には防げない。
  - パスワードを持つユーザーなら、そのログインで管理・公開環境・CLI・ログイン方法を変えることはできない。乗っ取りが続く間に限られる。
  - パスワードの無いユーザーは SSO が唯一の手段なので、そのアカウントは乗っ取られる。
- block や無効化をすると、そのサーバーのアカウントで入ったセッションを消す。block したときは、変えた backend がすぐ消し、ほかの backend も知らせ（`federation.policies.changed`）で覚えた方針をすぐ捨てる。無効化（環境変数）は 10 分ごとの定期掃除で。結び付き自体は残す。
- 偽のサーバーでアカウントを量産させないよう、新規登録は 1 つのサーバーから 1 時間に 30 件まで、IP ごとに 15 分で 10 件までにする。サーバーごとの件数は、数えてから作るまでをサーバーごとのロックで直列にする（同時の登録が同じ残りの枠を見て超えないように）。ドメインを使い捨てる攻撃には Bot 保護（C）が要る。
- レート制限は Express の側（`trust proxy` で取った IP、Redis で共有）で数える。開始 10 回/分、確認 60 回/分、登録の確定 10 回/15 分。better-auth の制限は、`X-Forwarded-For` が 2 段以上だと IP を取れず全員で 1 つの枠になる。これで絞ると 1 人で全員を止められるので、全体の上限としてだけ置く。
- 外部サーバーの応答の ID（英数字・`_`・`-` の 128 文字まで）とユーザー名（64 文字まで）は形を限る。DB と通知メールに入るためである。
- サーバーの入力では、IP の直書きを拒否する。本番では既定以外のポートも拒否する（公開 IP のポートを調べる手段にさせない）。
- 応答の照合でブラウザーの印が合わないときは、state の戻り先ではなく既定の画面に戻す（他人が始めた state で任意の origin へ飛ばさせない）。CORS が `*` のときも、戻り先は既定の origin だけにする。
- Mastodon のアプリの登録を忘れるのは、トークンの口が 401 を返したときだけにする（本人の取得の 401 では忘れない）。
- パスワードで作ったセッションそのものを奪われると、管理者の権限も使われる（管理の書き込みに直近の本人確認は求めない。B で決めた）。
- 奪われたセッションで、攻撃者が自分のフェディバースのアカウントやメールアドレスを足せる（パスワードの入れ直しを求めないため）。足した・外したことは連絡先メールに知らせ、設定の一覧で外せる。メールなしのユーザーには知らせる先が無い。
- 外部アカウントを外した後も、クッキーキャッシュ（最大 5 分）で確かめる API には、消したセッションが届きうる（既存の「ほかの端末をログアウト」と同じ）。管理・公開・ログイン方法の操作は DB のセッションで確かめる。

## コントロールパネルの「認証」（B）

既存の[コントロールパネル](../../packages/frontend/src/components/hud/tabs/ControlPanelTab.tsx)に「認証」を足し、ログイン画面に並べるサーバーを管理者が決める。

- 足す: ドメインを入れると、ログインと同じ判定（`lookup`）で名前・アイコン・種類を出す。判定に通らない（未対応・接続できない・許可の外・block）サーバーは足せない。12 件まで。
- 並べ替え・外す: その場で反映する（確定のボタンは挟まない）。並べ替えは今の一覧と同じ組だけ受け付け、ほかの管理者が同時に足し引きしていたら 409 で読み直させる。
- 足すのと並べ替えは、表ごとの advisory lock で直列にする（同時に足して上限を超えない）。
- 反映: 各 backend は一覧を 30 秒覚える。変えた backend はすぐ捨て、ほかの backend は知らせ（`auth.featured-servers.changed`）で捨てる。
- 後から使えなくなったサーバーは、ログイン画面では出ない（A と同じ）。コントロールパネルでは「ログイン画面に出ません」と印を付け、外せるようにする。
- 書き込みは既存の管理者の判定（DB のセッション・パスワードで確かめたセッション）だけで、直近の本人確認は求めない。
- API: `GET/POST /api/v1/admin/fediverse-servers`・`PUT /api/v1/admin/fediverse-servers/order`・`DELETE /api/v1/admin/fediverse-servers/:host`。どれも変えた後の一覧を返す。

### メールアドレスの追加（B）

メールなしで登録した人（SSO だけの人）が、設定の「ログイン方法」でメールアドレスを足す。足すとメールアドレスとパスワードでもログインでき、連絡先（お知らせ・ログイン方法の変更の知らせ）にもなる。管理者のロールも付けられるようになる。

1. アドレスとパスワード（8 文字以上）を入れると、確認コード（6 桁、10 分）を送る（`POST /api/v1/users/me/email`）。申し込みはユーザーごとに 1 つで、送り直すと前のコードは使えなくなる。
2. コードを入れると（`POST /api/v1/users/me/email/verify`）、同じトランザクションで内部値をそのアドレスに置き換え、パスワードの行を作る。このセッションはパスワードで確かめたものとして扱う（パスワードを決めた本人なので）。

- 保存するのはパスワードのハッシュとコードの HMAC だけ（`email_link_requests`）。コードは 5 回間違えたら申し込みを捨てる。
- 受け付けないもの: 形式の違うアドレス・`.invalid`・ほかのユーザーが使っているアドレス・既にメールアドレスかパスワードがある人。コードを送った後に同じアドレスで別の人が登録していたら、確かめた時点で断る（一意制約。外のトランザクションは savepoint で続け、申し込みを消す）。
- 送信は 15 分に 5 回、確かめは 15 分に 20 回まで（ユーザーごと）。メール確認を省く環境（`SKIP_EMAIL_VERIFICATION`）では、コードを送らずにすぐ足す。
- メールアドレスの変更・外すことはまだできない（パスワードの行は最後の手段として外せないのと同じ扱い）。

### アカウントの設定（B）

設定の「アカウント」は、Misskey の「セキュリティ」のように、アカウントの安全に関わるものを並べる。上から次の順にする。

1. パスワード: 「パスワードを変更」を押すとダイアログで今のパスワードと新しいパスワードを入れる（確認用にもう一度は入れさせず、表示で確かめられるようにする）。変えると、ほかの端末はログアウトする。パスワードの無い人には出さない。
2. ログイン方法: メールアドレス・フェディバースのアカウント。足す・外す。
3. ログイン中の端末: 期限内のセッションを新しく使った順に出す（端末の名前は User-Agent から、最後に使った時刻・入った方法・IP）。知らない端末は 1 つずつ、またはまとめてログアウトできる（`GET /api/v1/users/me/sessions`・`DELETE /api/v1/users/me/sessions/:id`）。パスワードを持つ人は、SSO だけのログインからは切れない（「ほかの端末をすべてログアウト」と同じ）。今の端末はメニューのログアウトで。
4. アカウントを削除。

ログイン方法の追加にパスワードを求めないので、乗っ取りに気付いて切れるよう、端末の一覧を置く。二要素認証（認証アプリ・パスキー）は、ログインそのものを奪われにくくする手段として後で足す（Better Auth の twoFactor・passkey）。

### ログイン方法の追加・解除でパスワードを求めない（B）

A では、奪われたセッションでログイン方法を足されないよう、追加・解除に直近の本人確認（パスワードの入れ直し）を求めていた。B では使い勝手を優先して外す。

- フェディバースのアカウントの追加・解除、メールアドレスの追加は、ログインしていれば（DB のセッションで確かめて）できる。
- 代わりに、追加と解除を確認済みの連絡先メールに知らせる。
- アカウントの削除は取り消せないので、引き続き直近の本人確認を求める。
- 管理者の権限は、引き続きパスワードで確かめたセッションだけで使える（メールなしの SSO だけのセッションには付かない）。

## ID でのログイン

パスワードでのログインは、メールアドレスの代わりに ID（`@` を付けても、大文字でもよい）でも入れる。better-auth の `/sign-in/email` に入る前に、ID をその人のメールアドレスに置き換える（`lib/signInIdentifierPlugin.ts`）。回数の制限・ボット対策・二段階認証は、メールアドレスで入れたときと同じに効く。

- いない ID は、誰のものでもないアドレスに置き換え、メールアドレスのときと同じ「メールアドレスかパスワードが違う」で断る（ID があるかを明かさない）。
- `@` を含む入力はメールアドレスとして扱う（`@ID@サーバー` のほかのサーバーのアカウントでは入れない）。

## メール送信と Bot 保護（C）

### メール送信

送信は [`lib/mail.ts`](../../packages/backend/src/lib/mail.ts) にまとめた（B）。環境変数 `SMTP_URL`（`smtps://` か STARTTLS 必須の `smtp://`）があれば SMTP、無ければ `RESEND_API_KEY` で Resend の API、どちらも無ければ送らない。送信元は `MAIL_FROM`。Resend は API の失敗を投げずに返すので、返り値を見て失敗にする。C では、これをコントロールパネルから設定できるようにする。

- SMTP では証明書を検証し、暗号化を必須にする。
- 接続先は DNS で解決したアドレスを検査してから使い、TLS 証明書は元のホスト名に対して検証する。
- テスト送信では、失敗した段階（接続・認証・送信元）を返す。 [Resend の SMTP 設定](https://resend.com/docs/send-with-smtp)

### 秘密の値

SMTP のパスワードや API キーなどの秘密は、DB にはデプロイ側の鍵で暗号化して置く。鍵の世代を値に持たせ、前の鍵でも読めるようにしておく（連合の鍵の移行と同じ考え方）。鍵を失った場合は環境変数の送信設定に戻る。

### Bot 保護

[ボット対策](bot-protection.md) に分けた。新規登録（メールアドレス・フェディバース）とパスワードでのログインを守る。ログイン試行・SSO 開始・OTP のレート制限は、ボット対策の有無にかかわらず適用する。
