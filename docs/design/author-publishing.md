# 作者の公開体験と公開環境（設計書）

対象ブランチ: `feat/author-publishing`（PR #177 `feat/world-identity` の上に積む）
前提: `docs/design/world-identity.md`（作者署名・作者アカウント・公開ルール）

## 1. 目的

作者は Web でも CLI でも CI でも、**ログインして「公開」するだけ**でワールドを公開できるようにする。
ワールド本体は Ubichill・GitHub Pages・任意のホストのどこに置いてもよい。読む側は配布場所とは別に
「内容が変わっていないこと」と「どの作者アカウントが公開したか」を確認する。

利用者には「秘密鍵」「ローテーション」を見せない。見せるのは **公開環境**（公開できるブラウザ・CLI・CI）の一覧と、その取り消しだけ。

### 完了の基準

1. 初めての作者が、鍵の説明を読まずに Web で公開できる。
2. 別の PC では、CLI でブラウザ認証するだけで公開できる。
3. CI（GitHub Actions など）から、ブラウザ操作なしで公開できる。
4. 取り消した公開環境の署名は、作者のサーバーでは即時に、ほかのサーバーでは **最長 T_max 以内に** 無効になる。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| 公開の権限 | **ログインできる = 公開できる**。ログイン済みの環境は、公開環境として自動で登録・署名できる |
| 取り消した鍵の署名 | **すべて無効**（取り消し前に署名した作品も含む）。作品は現役の公開環境で署名し直す |
| 作者の公開鍵 | 1 アカウントに複数（公開環境ごとに 1 本） |
| 秘密鍵 | 各環境の手元だけ。サーバーには預けない（署名もサーバーではしない） |
| アカウントの安全性 | 再認証・通知・2 段階認証は別途（#184） |

### なぜ「取り消した鍵の署名はすべて無効」か

署名には信頼できる時刻が入らないため、漏えいした鍵を持つ攻撃者は「取り消し前に署名したことにした作品」を作れる。
取り消し前の作品だけ残す方式（サーバーが公開のたびに時刻入りの受付記録を出す）は、公開のたびにサーバーがオンラインである必要があり、
どこに置いてもよい静的な成果物という前提と合わない。そのため単純で安全な方を取り、影響は「署名し直し」で吸収する（§7）。

## 3. 用語

- **作者アカウント**: `handle@domain`（表示は `@handle@domain`）。どこかのサーバーに実在するアカウント。
- **公開環境**: 署名して公開できる環境。種類は `browser` / `cli` / `ci`。それぞれ自分の署名鍵を 1 本持つ。
- **公開環境の一覧**: 作者のサーバーが管理する、そのアカウントの公開環境と公開鍵・取り消し状態の一覧。ほかのサーバーはこれを見て検証する。

## 4. データモデル（作者のサーバー）

`publishing_environments`（`users.signing_public_key` を置き換える）

| 列 | 内容 |
|---|---|
| `id` | 公開環境 ID |
| `user_id` | 作者アカウント |
| `kind` | `browser` / `cli` / `ci` / `legacy`（移行した旧 1 本鍵） |
| `name` | 表示名（例: 「Chrome on Mac」「ubichill CLI on work-pc」「GitHub Actions: owner/repo」） |
| `public_key` | ed25519 公開鍵（一意） |
| `api_token_hash` | CLI・CI がアップロードに使う API トークンのハッシュ（browser はセッションを使うので無し） |
| `created_at` / `last_used_at` | 追加日時・最終利用 |
| `revoked_at` | 取り消し日時（null なら有効） |

- **1 つの公開環境 = 署名鍵 + API の認証情報**。取り消すと両方が同時に止まる（署名はできないがアップロードはできる、という半端な状態を作らない）。
- 登録には、今と同じく所有証明（userId・公開鍵・時刻にその鍵で署名）を要求する。

## 5. 公開環境の一覧の公開（ほかのサーバー向け）

WebFinger の JRD から鍵一覧の文書へリンクする。

```
GET /.well-known/webfinger?resource=acct:youkan@ubichill.com
{
  "subject": "acct:youkan@ubichill.com",
  "properties": { "https://ubichill.com/ns/display-name": "ようかん" },
  "links": [{ "rel": "https://ubichill.com/ns/signing-keys", "href": "https://ubichill.com/api/v1/users/youkan/signing-keys" }]
}

GET /api/v1/users/youkan/signing-keys
{
  "account": "youkan@ubichill.com",
  "issuedAt": "2026-09-28T00:00:00Z",
  "keys": [
    { "publicKey": "…", "addedAt": "…" },
    { "publicKey": "…", "addedAt": "…", "revokedAt": "…" }
  ]
}
```

- **取り消した鍵は消さずに `revokedAt` 付きで残す**。消すと、検証側は「取り消された」のか「通信に失敗しただけ」なのかを区別できない。
- 移行期間中は、既存の単一の `https://ubichill.com/ns/ed25519-signing-key` プロパティも出す（旧実装の検証側のため）。

## 6. 検証ルール（読む側）

署名が作者アカウント付きで有効になるのは、署名鍵がその作者の公開環境の一覧にあり、かつ**取り消されていない**ときだけ。
取り消された鍵の署名は、いつ署名されたものでも作者を付けない（＝公開ルールを満たさず、一覧に出ない）。

### 有効期限（取り消しをほかのサーバーへ届けるため）

ほかのサーバーは確認結果（`author_bindings`）を保存して通常アクセスではネットワークに出ないが、保存したままだと取り消しに永久に気付かない。
分散型なので取り消しを通知して回ることもできない。そこで確認結果に期限を付け、**期限が取り消しの届く最長時間になる**。

| 状態 | 動作 |
|---|---|
| 確認から T_fresh 以内 | 保存した結果をそのまま使う（ネットワークに出ない） |
| T_fresh 超過 | 保存した結果で即答し、裏で鍵一覧を取り直す |
| 取り直しで `revokedAt` あり | 直ちに作者を外す |
| 取り直しに失敗（相手が落ちている） | T_max までは保存した結果を使い続け、超えたら作者を外す |

初期値の案: T_fresh = 1 時間、T_max = 24 時間（完了の基準 4 の「最長 T_max」）。
`worlds/trusted-authors.json`（レビュー済みの公式アカウントの記録）は期限なし。複数の鍵と `revokedAt` を持てる形式にする。

## 7. 取り消しと署名し直し

サーバーは秘密鍵を持たないので、署名し直しは作者の現役の公開環境で行う。

- **通常の交換**（新しい PC に移る等）: 新しい環境を追加 → 作品を署名し直す → 古い環境を取り消す。作品は途切れない。
- **緊急の取り消し**（紛失・漏えい）: 直ちに取り消す → そのアカウントの本体に置いたワールドは「署名し直しが必要」になり非公開 →
  次に Web で開いたとき、または `ubichill publish --resign-all` で、現役の環境でまとめて署名し直す。
- **外部ホスト（GitHub Pages 等）に置いた作品**: 署名ファイルを置き直す必要がある。CI で公開している場合は、CI を再実行すれば新しい鍵で署名される。
- アカウント設定に「署名し直しが必要なワールド」の一覧を出す。

## 8. Web の流れ

1. ログインしてワールドを作る。
2. 「公開する」を押す。このブラウザが公開環境でなければ、**自動で鍵を作り、公開環境として登録する**（ログイン済み = 公開できる、なので確認は出さない）。
   ID 未設定なら、その場で ID だけ決めてもらう。
3. 署名して公開。次回からは「公開する」だけ。
4. アカウント設定の「公開できるブラウザ・CLI・CI」で一覧と取り消し。

- ブラウザのデータを消すと、その公開環境は使えなくなる（一覧に残る）。次に公開するとき自動で新しい環境が追加される。
  使われなくなった環境は「最終利用が古い」として一覧で目立たせ、取り消しを促す。
- 現在の「鍵ファイルのダウンロード・読み込み」は通常の導線から外す。

## 9. CLI の流れ

```
ubichill login [--server=https://ubichill.com]
  → CLI が手元で鍵を作る
  → ブラウザを開いてログイン（RFC 8252: ループバックへのリダイレクト）
    ブラウザを開けない環境では、表示した短いコードを別の端末で承認（RFC 8628: デバイス認可）
  → 公開環境（kind=cli）として公開鍵を登録し、API トークンを受け取る
  → ~/.config/ubichill/credentials/<server>/<handle>.json（0600）に保存

ubichill publish world.yaml
  → mod を固定（今の install）
  → 作者アカウント付きで署名（--author 不要。ログインしたアカウントを使う）
  → 本体へ公開: アップロードまで行う
    外部ホストへ公開（--out=<dir>）: 署名済みの world.yaml / .lock.json / .sig.json を出力する
```

- 認証（ログイン）と配置（アップロード／ファイル出力）は分ける。
- `ubichill keygen` / `sign --key-file` / `--author` は上級者向けとして残す（§10 の CI も同じ仕組みの上に乗る）。
- better-auth にデバイス認可の仕組みがあるかは実装時に確認する。無ければ自前で実装する（短いコード + ポーリング）。

## 10. CI の流れ

CI ではブラウザ操作ができないので、**CLI で CI 用の公開環境を作り、その認証情報を CI の Secret に入れる**。

```
# 手元で 1 回だけ（ログイン済みの CLI から）
ubichill ci create --name "GitHub Actions: owner/repo"
  → CI 用の鍵を作り、公開環境（kind=ci）として登録
  → 鍵・API トークン・アカウントをまとめた 1 本の文字列を表示（この場限り。サーバーには鍵を保存しない）

# CI（GitHub Actions）
env:
  UBICHILL_CREDENTIALS: ${{ secrets.UBICHILL_CREDENTIALS }}
run: npx ubichill publish worlds/my-world.yaml --out=dist/
```

- CI 用の公開環境も一覧に出て、ブラウザ・CLI と同じように取り消せる。取り消したら、その CI の署名はすべて無効（§2）。
- 鍵の漏えい時は、取り消して `ubichill ci create` し直し、Secret を差し替えて CI を再実行すれば、全作品が新しい鍵で署名し直される。
- 将来の選択肢: GitHub Actions の OIDC（npm の Trusted Publishing と同じ方式）で、長期の Secret を置かずに公開する。
  ただし実行ごとの使い捨て鍵と「取り消した鍵の署名はすべて無効」の兼ね合い（期限切れと取り消しを区別する必要）があるので別途検討（issue）。

## 11. 移行

- 既存の `users.signing_public_key` は、公開環境（kind=`legacy`, name=「以前の鍵」）として 1 件移す。既存の作品の署名はそのまま有効。
- 既存の「鍵ファイルを読み込む」導線で使っていた鍵は、読み込んだ時点でそのブラウザの公開環境として登録する。
- 旧 `https://ubichill.com/ns/ed25519-signing-key` プロパティは移行期間だけ出し続け、その後削除する。
- ほかのサーバーの `author_bindings` は「アカウント → 鍵一覧 + 取得時刻」を保存する形に変える（今は 1 本の鍵）。
