# 作者の公開体験と公開環境（設計書）

前提: `docs/design/world-identity.md`（作者署名・作者アカウント・公開ルール）

## 1. 目的

作者は Web でも CLI でも CI でも、**ログインして「公開」するだけ**でワールドを公開できるようにする。
ワールド本体は Ubichill・GitHub Pages・任意のホストのどこに置いてもよい。読む側は配布場所とは別に
「内容が変わっていないこと」と「どの作者アカウントが公開したか」を確認する。

利用者には「秘密鍵」「ローテーション」を見せない。見せるのは **公開環境**（公開できるブラウザ・CLI・CI）の一覧と、その取り消しだけ。

### 完了の基準

1. 初めての作者が、鍵の説明を読まずに Web で公開できる。
2. 別の PC では、CLI でブラウザ認証するだけで公開できる。
3. CI（GitHub Actions など）から、ブラウザ操作なしで公開できる。
4. 取り消した公開環境の署名は、作者のサーバーでは即時に無効になる。ほかのサーバーでは、作者のサーバーが動いていれば、確認から T_fresh を過ぎた後の最初のアクセスで裏で取り直し、外部ワールドのキャッシュ（5 分）が切れた後のアクセスで無効になる（最短でも T_fresh ＋ 5 分、かつアクセスがあった後）。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| 公開の権限 | **ログインできる = 公開できる**。ログイン済みの環境は、公開環境として自動で登録・署名できる |
| 取り消した鍵の署名 | **すべて無効**（取り消し前に署名した作品も含む）。作品は現役の公開環境で署名し直す |
| 作者の公開鍵 | 1 アカウントに複数（公開環境ごとに 1 本） |
| 秘密鍵 | 各環境の手元だけ。サーバーには預けない（署名もサーバーではしない） |
| アカウントの安全性 | 再認証・通知・2 段階認証は別途（#184） |

### なぜ「取り消した鍵の署名はすべて無効」か

署名には信頼できる時刻が入らないため、漏えいした鍵を持つ攻撃者は「取り消し前に署名したことにした作品」を作れる。
取り消し前の作品だけ残す方式（サーバーが公開のたびに時刻入りの受付記録を出す）は、公開のたびにサーバーがオンラインである必要があり、
どこに置いてもよい静的な成果物という前提と合わない。そのため単純で安全な方を取り、影響は「署名し直し」で吸収する（§7）。

## 2.1 信頼モデル（何を信じているか）

- **作者のホームサーバー（作者アカウントを発行したサーバー）の運営者は、その作者を名乗れる。** 鍵一覧を管理しているのはホームサーバーなので、
  運営者が鍵を足せば本人として署名できる。Mastodon などの WebFinger を使う分散 SNS と同じ信頼モデルで、設計として受け入れる。
  これを避けたい作者は、自分のドメインで作者アカウントを運用する（#181）。
- ほかのサーバーは、作者のホームサーバーが返す鍵一覧を信じる。改竄検知（内容が署名時から変わっていないこと）は暗号で保証する。
- 公式アカウント（`ubichill@ubichill.com`）だけは、リポジトリの記録（`worlds/trusted-authors.json`、PR でレビュー）を信じ、ネットワークに出ない。

## 3. 用語

- **作者アカウント**: `handle@domain`（表示は `@handle@domain`）。どこかのサーバーに実在するアカウント。
- **公開環境**: 署名して公開できる環境。種類は `browser` / `cli` / `ci`。それぞれ自分の署名鍵を 1 本持つ。
- **公開環境の一覧**: 作者のサーバーが管理する、そのアカウントの公開環境と公開鍵・取り消し状態の一覧。ほかのサーバーはこれを見て検証する。

## 4. データモデル（作者のサーバー）

`publishing_environments`（`users.signing_public_key` を置き換える）

| 列 | 内容 |
|---|---|
| `id` | 公開環境 ID |
| `user_id` | 作者アカウント |
| `kind` | `browser` / `cli` / `ci` / `legacy`（移行した旧 1 本鍵） |
| `name` | 表示名（例: 「Chrome on Mac」「ubichill CLI on work-pc」「GitHub Actions: owner/repo」） |
| `public_key` | ed25519 公開鍵（一意） |
| `api_token_hash` | CLI・CI がアップロードに使う API トークンのハッシュ（browser はセッションを使うので無し） |
| `created_at` / `last_used_at` | 追加日時・最終利用 |
| `revoked_at` | 取り消し日時（null なら有効） |

- **1 つの公開環境 = 署名鍵 + API の認証情報**。取り消すと両方が同時に止まる（署名はできないがアップロードはできる、という半端な状態を作らない）。
- 登録には、今と同じく所有証明（userId・公開鍵・時刻にその鍵で署名）を要求する。

## 5. 公開環境の一覧の公開（ほかのサーバー向け）

WebFinger の JRD から鍵一覧の文書へリンクする（鍵一覧の URL は WebFinger と同じオリジンに限る）。

```
GET /.well-known/webfinger?resource=acct:youkan@ubichill.com
{
  "subject": "acct:youkan@ubichill.com",
  "properties": { "https://ubichill.com/ns/display-name": "ようかん" },
  "links": [{ "rel": "https://ubichill.com/ns/signing-keys", "href": "https://ubichill.com/api/v1/authors/youkan/signing-keys" }]
}

GET /api/v1/authors/youkan/signing-keys
{
  "account": "youkan@ubichill.com",
  "issuedAt": "2026-09-28T00:00:00Z",
  "keys": [
    { "publicKey": "…", "addedAt": "…" },
    { "publicKey": "…", "addedAt": "…", "revokedAt": "…" }
  ]
}
```

- **取り消した鍵は消さずに `revokedAt` 付きで残す**。消すと、検証側は「取り消された」のか「通信に失敗しただけ」なのかを区別できない。
- 旧来の単一の `https://ubichill.com/ns/ed25519-signing-key` プロパティは出さない（利用者がほぼいないので移行期間を設けない）。

## 6. 検証ルール（読む側）

署名が作者アカウント付きで有効になるのは、署名鍵がその作者の公開環境の一覧にあり、かつ**取り消されていない**ときだけ。
取り消された鍵の署名は、いつ署名されたものでも作者を付けない（＝公開ルールを満たさず、一覧に出ない）。

### 有効期限（取り消しをほかのサーバーへ届けるため）

ほかのサーバーは確認結果（`author_bindings`）を保存して通常アクセスではネットワークに出ないが、保存したままだと取り消しに永久に気付かない。
分散型なので取り消しを通知して回ることもできない。そこで確認結果に期限を付けて取り直す。

**取得の失敗と取り消しは区別できる**（取り消しは鍵一覧に `revokedAt` として載る）。
取り直しはアクセスがあったときに裏で行う（stale-while-revalidate）。T_fresh を過ぎた後の最初のアクセスはまだ古い結果で答え、
さらにワールドの解決結果は外部ワールドのキャッシュに 5 分残る。そのため取り消しが届くのは「T_fresh ＋ 5 分、かつアクセスがあった後」。
取り直せない（作者のサーバーが止まっている）ときは、最後に確認できた結果を長めに使い、「確認が古い」と表示する。
T_max を短くすると、小さな自前サーバーの短い障害で作者のワールドがほかのサーバーの一覧から消え、安定した大きいサーバーに集まる方向に働く
（分散の考え方に逆行する）。一方、小さい自前サーバーを止めるのは攻撃者にとって容易で、狙い撃ちなら「鍵の盗難」と「作者のサーバーの停止」は
独立に起きない。そこで**確認が古い間は、古くなる前に確認済みだった内容（contentHash）にだけ作者を付ける**
（`author_confirmed_contents`）。既存の作品は一覧から消えず、盗んだ鍵で新しく出した作品には、作者のサーバーを止めても作者が付かない。
盗んだ鍵で既存の作品と同じ内容に署名しても、内容は本人のものなので害はない。

| 状態 | 動作 |
|---|---|
| 確認から T_fresh 以内 | 保存した結果をそのまま使う（ネットワークに出ない） |
| T_fresh 超過 | 保存した結果で即答し、裏で鍵一覧を取り直す |
| 取り直しで `revokedAt` あり | 直ちに作者を外す |
| 取り直しに失敗（相手が落ちている） | T_max までは保存した結果を使い続ける。確認から 24 時間を超えたら「確認が古い」と表示し、それまでに確認済みだった内容にだけ作者を付ける。T_max を超えたら作者を外す |

決定: T_fresh = 1 時間、T_max = 14 日。識別結果に最後に確認できた時刻（`authorCheckedAt`）を載せ、画面はそれで「確認が古い」を判定する。

### 取得の上限（作者名を変えた問い合わせへの対策）

作者を名乗るだけならだれでも署名できるので、作者名を変えた署名（`a1@victim`, `a2@victim`, …）を読ませれば、そのドメインへの取得を出させられる。
そこで**初めての作者・知らない鍵の取得だけ**、ドメインごとに 1 分 60 回までにする。保存済みの作者の取り直しは、作者ごとに T_fresh に 1 回で
数が限られるので上限をかけない（攻撃者が上限を使い切って、既知の作者の取り直し＝取り消しの伝達を止められないように）。

- 上限に達して確かめられなかった作者は `pending`（作者は付けず、識別結果に `authorPending` を付ける）。外部ワールドのキャッシュは 30 秒にして、
  窓が空いたら確認し直す。作者の多いサーバーの一覧を初めて表示したときは、順に作者が付いていく。
- 失敗の記録・ドメインごとの回数などのメモリ上の記録は、項目数に上限を付け、古いものから捨てる。
- 実在する作者名に知らない鍵を付けて名乗れば、作者 1 人あたり 1 分に 1 回の取得を起こせるので、作者の多いドメインでは上限を使い切れる。
  影響は新しい作者・新しい公開環境の反映が pending で遅れるだけで、作者が外れることはないので許容する。
- 作者の確認処理の例外（DB エラーなど）も pending になり 30 秒ごとに確認し直し続けるので、ログを出して障害に気付けるようにする。
`worlds/trusted-authors.json`（レビュー済みの公式アカウントの記録）は期限なし。複数の鍵と `revokedAt` を持てる形式にする。

## 7. 取り消しと署名し直し

サーバーは秘密鍵を持たないので、署名し直しは作者の現役の公開環境で行う。

- **通常の交換**（新しい PC に移る等）: 新しい環境を追加 → 作品を署名し直す → 古い環境を取り消す。作品は途切れない。
- **緊急の取り消し**（紛失・漏えい）: 直ちに取り消す → そのアカウントの本体に置いたワールドは「署名し直しが必要」になり非公開 →
  次に Web で開いたとき、または `ubichill publish --resign-all` で、現役の環境でまとめて署名し直す。
- **外部ホスト（GitHub Pages 等）に置いた作品**: 署名ファイルを置き直す必要がある。CI で公開している場合は、CI を再実行すれば新しい鍵で署名される。
- **取り消すときに理由を選ぶ**: 「紛失した・データを消した」か「漏えい・心当たりがない」。
- アカウント設定に「取り消した鍵で署名したワールド」を、署名した公開環境の名前と最終更新日時つきで出す。未署名のワールドは、本人が非公開のつもりかもしれないので含めない。
  - 紛失で取り消した鍵の分は「まとめて署名し直す」。1 つ失敗しても残りは続け、失敗したワールドと理由を示す。
  - **漏えい（または理由の記録が無い取り消し）の鍵の分は、まとめて署名し直す対象にしない。** 乗っ取った攻撃者が内容を書き換えて署名した
    ワールドに、本人の現役の鍵でまとめて署名し直すと、攻撃者の内容が本人の作品として公開されるため。エディタで中身を確かめてから 1 つずつ署名し直させる。

### 乗っ取られたとき

- **新しい公開環境が追加されたら、メールで知らせる**（心当たりがなければ漏えいとして取り消し、パスワードを変える）。画面でも、追加から 7 日は「新しい」と目立たせる。
- **漏えいとして取り消したら、ほかの端末のログアウトとパスワードの変更へ案内する。** 公開環境を取り消しても攻撃者のログインは残り、
  新しい環境をすぐに登録し直せるため。「ほかの端末をすべてログアウト」（いまのログイン以外のセッションを無効にする）を画面から押せる。
- 再認証・2 段階認証など、そもそも乗っ取られにくくする対策は #184。

## 8. Web の流れ

1. ログインしてワールドを作る。
2. 「公開する」を押す。このブラウザが公開環境でなければ、**自動で鍵を作り、公開環境として登録する**（ログイン済み = 公開できる、なので確認は出さない）。
   ID 未設定なら、その場で ID だけ決めてもらう。
3. 署名して公開。次回からは「公開する」だけ。
4. アカウント設定の「公開できるブラウザ・CLI・CI」で一覧と取り消し。

- ブラウザのデータを消すと、その公開環境は使えなくなる（一覧に残る）。次に公開するとき自動で新しい環境が追加される。
  使われなくなった環境は「最終利用が古い」として一覧で目立たせ、取り消しを促す。
- 現在の「鍵ファイルのダウンロード・読み込み」は通常の導線から外す。

## 9. CLI の流れ

```
ubichill login [--server=https://ubichill.com] [--device]
  → CLI が手元で鍵を作る（秘密鍵は手元だけ）
  → ブラウザで承認する（ログインしていなければログインしてから）
      既定: RFC 8252 のループバック。CLI が 127.0.0.1 の一時ポートで待ち、承認後のリダイレクトで認可コードを受け取る
      --device: RFC 8628 のデバイス認可。表示した短いコードを別の端末のブラウザで承認し、CLI はポーリングで待つ
  → CLI が「認可コード（またはデバイスコード）＋ 鍵の所有の証明」を送り、公開環境（kind=cli）と API トークンを受け取る
  → ~/.config/ubichill/credentials.json（0600）に保存（サーバーごと）

ubichill publish world.yaml [--server=…] [--out=<dir>]
  → mod を固定（install と同じ）
  → 作者アカウント付きで署名（--author 不要。ログインしたアカウントを使う）
  → 本体へ公開: 初回は作成し、以後は同じワールドを更新する（対応は <world>.ubichill.json に記録。秘密は含まない）
      サーバーが保存する値（prepare）に署名し、内容と署名を一緒に送る（Web と同じ。サーバーは metadata.name を自分の ID にする）
    外部ホストへ公開（--out=<dir>）: 署名済みの world.yaml / .lock.json / .sig.json を出力する

ubichill whoami   # 使っている認証情報（サーバー・作者アカウント・公開環境）
ubichill logout   # この端末の公開環境を取り消し（紛失として）、認証情報を消す
```

### 認可の手順（サーバー側）

| 手順 | API | 認証 |
|---|---|---|
| 1. 要求を作る | `POST /api/v1/cli-auth/requests` `{ kind, name, publicKey, redirectUri?, codeChallenge? }` → `{ requestId, approveUrl, userCode?, deviceCode? }` | なし |
| 2. 内容を見る | `GET /api/v1/cli-auth/requests/:id`（または `?userCode=`） | ログイン |
| 3. 承認する | `POST /api/v1/cli-auth/requests/:id/approve` → ループバックならリダイレクト先（`?code=&state=`） | ログイン（DB のセッション） |
| 4. 引き換える | `POST /api/v1/cli-auth/token` `{ requestId, code+codeVerifier | deviceCode, signature }` → `{ token, account, environment }` | 鍵の所有の証明 |

- **要求は 10 分で失効し、1 回しか引き換えられない**。承認されていない要求の引き換えは「承認待ち」（デバイス認可のポーリング用）。
- **ループバックは PKCE（S256）で認可コードを要求に結び付ける**。リダイレクト先は `http://127.0.0.1:<port>/…` か `http://localhost:<port>/…` に限る。
  横取りされた認可コードだけでは引き換えられない。
- **鍵の所有の証明**: 引き換え時に `ubichill-cli-auth:<requestId>` に要求の公開鍵で署名させる。公開環境はこの時点で作る
  （承認したが引き換えられなかった要求で、だれも持っていない鍵が登録されることはない）。
- **デバイス認可のフィッシング**（攻撃者が自分の要求のコードを本人に承認させる）への対策: 承認画面に「CLI に表示されたコードと
  同じか」を確かめさせ、環境の名前・種類・鍵の指紋を出す。承認すると公開環境が追加された通知メールが届く。既定はループバック。
- 承認画面の操作は、公開環境の登録と同じく DB のセッションを確かめる（ログアウトさせたセッションでは承認できない）。

### API トークン

- 形式は `ubi_<32 byte の乱数>`。サーバーは sha256 だけを保存する（`publishing_environments.api_token_hash`）。**トークン = 公開環境**で、
  公開環境を取り消すとトークンも同時に使えなくなる。
- **使える操作は公開に関わるものだけ**: 自分のアカウント情報、ワールドの作成・prepare・更新・署名の保存、自分のワールドの一覧、
  自分の公開環境の取り消し（logout）。パスワード・ほかの公開環境・お気に入り・セッションの操作には使えない。
- **トークンで送る署名は、そのトークンの公開環境の鍵で署名したものに限る**（盗まれたトークンで別の鍵の署名を通させない）。
- 最終利用時刻を記録し、一覧で「長く使われていない」を出す。

## 10. CI の流れ

CI ではブラウザ操作ができないので、**手元で CI 用の公開環境をブラウザで承認し、その認証情報を CI の Secret に入れる**。

```
# 手元で 1 回だけ
ubichill ci create --name "GitHub Actions: owner/repo" [--server=…]
  → CI 用の鍵を作り、ブラウザで承認して公開環境（kind=ci）として登録（login と同じ手順。CLI のトークンでは作らない）
  → 鍵・API トークン・サーバー・アカウントをまとめた 1 本の文字列を表示（この場限り。手元にもサーバーにも鍵を保存しない）

# CI（GitHub Actions）
env:
  UBICHILL_CREDENTIALS: ${{ secrets.UBICHILL_CREDENTIALS }}
run: npx ubichill publish worlds/my-world.yaml            # 本体へ
run: npx ubichill publish worlds/my-world.yaml --out=dist/ # GitHub Pages など外部へ
```

- CI 用の公開環境を CLI のトークンで作れないようにするのは、盗まれた CLI のトークンから新しい鍵を増やさせないため（鍵を増やすのは必ずブラウザの承認）。
- CI 用の公開環境も一覧に出て、ブラウザ・CLI と同じように取り消せる。取り消したら、その CI の署名はすべて無効（§2）。
- 鍵の漏えい時は、取り消して `ubichill ci create` し直し、Secret を差し替えて CI を再実行すれば、全作品が新しい鍵で署名し直される。
- 将来の選択肢: GitHub Actions の OIDC（npm の Trusted Publishing と同じ方式）で、長期の Secret を置かずに公開する。
  ただし実行ごとの使い捨て鍵と「取り消した鍵の署名はすべて無効」の兼ね合い（期限切れと取り消しを区別する必要）があるので別途検討（issue）。

## 10.1 mod の公開（設計のみ。実装は mod のホスティングと一緒に行う）

mod もワールドと同じく**作者アカウントで署名して公開する**。認証・鍵・トークンはワールドと共通にし、mod のために別の仕組みを作らない。

- **認証**: 同じ公開環境と API トークンを使う（`ubichill login` / `ubichill ci create` のまま）。トークンの使える操作に「mod の公開」を加える。
- **署名の対象**: mod の配布物（worker の hash・manifest・capability の上限・version）を正規化した値に、作者アカウント付きで署名する
  （ワールドの署名と同じ形式で、`kind: "mod"` と `modId` を入れる）。lock はワールドが「どの mod のどのバイト列を使うか」を固定し、
  mod の署名は「その mod をだれが出したか」を示す。どちらか一方では足りない（lock は作者を示さず、署名は使う版を固定しない）。
- **識別子**: `acct:handle@domain/modId`。名前の取り合い（同じ modId の別作者）は作者アカウントで区別する。
- **権限（capability）の許可**: 利用者が「この mod に外部通信を許可」したときの記録は、URL ではなく `作者アカウント + modId` に結び付ける
  （同じ作者の新しい版は許可を引き継ぐ。別の作者の同名 mod は引き継がない）。capability の上限が広がった版は、改めて確認する。
- **公開の CLI**: `ubichill publish mods/<mod>`（本体のホスティングへ）／`--out=<dir>`（GitHub Pages など）。ワールドと同じく
  ログインしたアカウントで署名する。
- **取り消し**: ワールドと同じく、取り消した鍵の署名は作者を付けない。利用者の許可（作者アカウント + modId）は、
  作者が確認できない mod には使わない。
- 未決: mod のホスティング（本体に置くか、配布元 URL のままにするか）、公開済み mod の版の固定と取り下げ。

## 11. 移行

- 既存の `users.signing_public_key` は、公開環境（kind=`legacy`, name=「以前の鍵」）として 1 件移す。既存の作品の署名はそのまま有効。
- 既存の「鍵ファイルを読み込む」導線で使っていた鍵は、読み込んだ時点でそのブラウザの公開環境として登録する。
- 旧 `https://ubichill.com/ns/ed25519-signing-key` プロパティは移行期間を設けず削除する。
- ほかのサーバーの `author_bindings` は「アカウント → 鍵一覧 + 取得時刻」を保存する形に変える。旧形式の行は取り直せるキャッシュなので移行時に捨てる。

## 13. 未決事項

- CI の OIDC 方式（使い捨て鍵の扱い）を入れるか。
- **古い版への差し戻し**: 署名に版の番号（単調に増える値）が無いので、同じ作者が過去に署名した古い版（脆弱な mod を固定した版など）を
  配信元が再び配信すると、検証は通る。署名に版の番号を入れ、受け手が見たことのある最大の番号より小さい版を警告するかを決める。
- 公開環境の数の上限（無制限だと取り消し忘れの鍵が溜まる）。
- 外部ホストの作品が「署名し直しが必要」になったことを作者にどう知らせるか（作者のサーバーは外部の作品を把握していない）。
