# ボット対策

新規登録とパスワードでのログインで、ボットでないことを外部のサービス（Cloudflare Turnstile か hCaptcha）で確かめる。管理者がコントロールパネルで設定する。フェディバースのログインと認証設定の全体は [フェディバースログインと認証設定](fediverse-sign-in.md) を参照。

## できること

- コントロールパネルの「認証」→「ボット対策」で、使わない・Cloudflare Turnstile・hCaptcha から選ぶ。
  1. サービスのダッシュボードで作ったサイトキーとシークレットキーを入れる。
  2. 出てきたウィジェットで確かめる。
  3. 「保存」を押す。
- 使っている間は、次の 3 つでウィジェットを通さないと進めない。
  - メールアドレスでの新規登録
  - フェディバースのアカウントでの新規登録（ID と表示名を決める画面）
  - パスワードでのログイン（メールアドレスでも ID でも）
- 「使わない」にして保存すると、鍵ごと消える。

## 決めたこと

| 決めたこと | 理由 |
| --- | --- |
| 新規登録とパスワードでのログインを守る | 登録はアカウントの量産、パスワードのログインは総当たり・使い回しのパスワードを狙われる。検証サービスが止まるとパスワードでのログインも止まるが、フェディバースでのログインは使える。 |
| フェディバースでのログインと、二段階目のコードには求めない | フェディバースでのログインは相手のサーバーで本人を確かめる。二段階目はパスワードを通った後で、回数の上限もある。 |
| サービスは Turnstile と hCaptcha | どちらも無料で、検証の API の形が同じ。Cloudflare に寄せたくない管理者のために 2 つから選べるようにした。reCAPTCHA は Google Cloud のプロジェクトが要るので入れていない。 |
| 保存の前に、入れた鍵の組で確かめて通ることを求める | 鍵を間違えたまま保存すると、新規登録が全部止まる。サイトキーにこのサーバーのホスト名が入っていない場合も、ここで分かる。 |
| 本番ではテスト用の鍵を受け付けない | テスト用の鍵はいつも通るので、保存してもボットを止めない。開発環境では手元の確認のために通す。 |
| 確かめられないときは登録を止める | 検証サービスにつながらない・保存した鍵を読めないときに通すと、ボット対策を外したのと同じになる。止めた理由は応答の `code` で返す。 |

## 仕組み

### 登録のとき

1. 登録・ログインの画面は `GET /api/v1/users/bot-protection` でサービスとサイトキーを読む。使っていなければ `null` で、外部のスクリプトは読み込まない。ウィジェットは、パスワードで入ろうとしてから読み込む（画面を見ただけ・フェディバースで入る人には外部のスクリプトを読ませない。トークンの期限切れも起きにくい）。ログイン・メールアドレスでの新規登録とも、パスワードを入れ始めたときに出す。場所は前もって取らず、出たぶんだけボタンが下がる。
2. ウィジェットで確かめたトークンを、`x-bot-check` ヘッダーで送る（フェディバースの登録は better-auth の口なので、Express で本文を読まずに済むヘッダーにした）。
3. backend は、回数の制限の後で検証サービスに問い合わせる（[`middleware/botCheck.ts`](../../packages/backend/src/middleware/botCheck.ts)）。照合するのは次のもの。

| 照合するもの | 理由 |
| --- | --- |
| 通ったか（`success`） | |
| ホスト名が、Ubichill の公開 URL（`BETTER_AUTH_URL`・`PUBLIC_BASE_URL`・`CORS_ORIGIN`）のもの | ほかのサイトで取ったトークンを使わせない。 |
| action が、その画面のもの（Turnstile だけ。`sign-in`・`sign-up`・`fediverse-sign-up`） | 別の画面で取ったトークンを使わせない。hCaptcha は action を返さない。 |
| 同じトークンを 2 回使っていない | 検証サービスが断る（Turnstile の `timeout-or-duplicate`、hCaptcha の `already-seen-response`）。 |

トークンは 1 回しか使えない。画面は送るたびにウィジェットを作り直す。登録が別の理由（ID が使われているなど）で失敗した後も同じ。ボット対策で断られたときは、設定も読み直す（画面を開いた後に管理者がサービスやサイトキーを変えても、古いウィジェットのまま行き詰まらない）。

失敗の種類は応答の `code` で返す（shared の `BOT_CHECK_ERRORS`）。

| `code` | 状態 | いつ |
| --- | --- | --- |
| `bot-check-required` | 400 | トークンが無い |
| `bot-check-failed` | 400 | 通らない・期限切れ・使い回し・ホスト名や action が違う |
| `bot-check-unavailable` | 503 | 検証サービスにつながらない（5 秒で切る）・内部エラー |
| `bot-check-misconfigured` | 503 | 保存した鍵を読めない・検証サービスが鍵を受け付けない（管理者の対応が要る。ログに残す） |

### 設定の保存

- コントロールパネルのウィジェットは action `bot-protection-settings` で確かめる。
- backend は、送られた鍵の組でそのトークンを確かめてから保存する（`PUT /api/v1/admin/bot-protection`）。
- シークレットキーを空のまま保存すると、保存済みのもの（同じサービスのときだけ）を使う。
- シークレットキーは画面に返さない。

### 鍵の保存

- `bot_protection_settings`（1 行だけ。無ければ使わない。migration 0043）。
- シークレットキーは [二段階認証](two-factor.md) の鍵と同じく、サーバーの秘密から HKDF で作った鍵で AES-256-GCM で暗号化する。
  - 追加の認証データにサービスとサイトキーを入れ、行のサイトキーだけを書き換えても開けないようにする。
  - `BETTER_AUTH_SECRETS` で秘密を入れ替えるときは、古い秘密を一覧に残す。外すとシークレットキーを開けなくなり、新規登録が止まる。コントロールパネルにその旨を出すので、入れ直すか使わないにする。
- 設定は backend ごとに 30 秒覚える。変えた backend はすぐ捨て、ほかの backend には知らせ（`auth.bot-protection.changed`）で捨てさせる。

## 残り

- **本物の鍵での確認:** Turnstile・hCaptcha の本物の鍵での保存と登録。プレビュー環境（`NODE_ENV=production`）では、テスト用の鍵は使えない。手元では、両方のテスト用の鍵で、保存・登録・使わないにする・秘密の入れ替えを確かめた。
- 負荷試験や E2E のように、1 つの IP から多くの人を登録する環境では使わない（ボット対策がそれを止める）。
