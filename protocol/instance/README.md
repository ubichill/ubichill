# インスタンスプロトコル v1

HTTPの契約は `openapi.json`、WebSocketのイベント一覧とフレームは `asyncapi.json`。
`pnpm protocol:generate` でGoとTypeScriptのHTTP型を生成する。生成物はコミットし、CIで差分を確認する。
mod SDKのHost/Workerプロトコルとは独立したバージョンである。

## 接続

1. SNSモードではSNSが認証・フレンド・パスワードを検証し、管理APIで対象インスタンスの参加チケットを発行する。
2. 単体モードでは `/realtime/v1/instances/{id}/guest` がゲストIDを発行する。
3. 返されたURLをWebSocketで開き、最初の10秒以内に `world:join` を送る。

```json
{"event":"world:join","id":"request-1","data":{"instanceId":"standalone","token":"opaque-ticket","user":{"name":"Guest","position":{"x":0,"y":0},"status":"online"}}}
```

チケットはURLやCookieに入れない。インスタンス・参加者・期限・種別・部屋の世代（クラスタの `gen` と owner の `epoch`）を
HMACで検証する不透明な値として扱う。発行するのは部屋の owner で、入室時に今の部屋の世代と一致しなければ `ticket_invalid` にする。
同じ部屋IDで作り直された部屋（owner の交代・自己停止・Redis の消失のあと）に、前の部屋のチケットを通さないため。
ゲストの再接続情報も、世代が違えば新しいゲストIDを発行する。
署名鍵は `INSTANCE_TICKET_KEY` があればそれ、無ければ管理トークンからHMAC-SHA256で派生する（用途の名前 `ubichill instance ticket v1`）。
全Podで同じ鍵になり、再起動してもチケットは無効にならない。管理トークンの無い単体モード（`--guests`）だけ起動ごとに生成する。
SNSチケットは2分、ゲストの再接続情報は24時間有効。
Goが複数のPodで動くとき、接続を受けたPodは部屋のownerのPodへ `world:join` から先を中継する（クライアントから見たフレームは変わらない）。
ownerが接続を閉じたら中継も閉じるので、クライアントはいつもどおりチケットを取り直して繋ぎ直す。
例外は scale-in の引っ越し（ownerだけを別のPodへ移す）で、接続は切れない。引っ越しの間（通常は数十ms）、変更系の要求は
`{"success":false,"error":"…","code":"migrating"}` になり状態は変わらないので、少し待って同じ操作を送り直してよい
（応答の要らないカーソル・ephemeral・IDの無いpatchは捨てられる）。引っ越しのあと `users:update`・`world:snapshot` がもう一度届く（入退室の通知は出ない）。
止めるPodは、直接繋いでいるクライアントへ切断の前（既定10分前）に `{"event":"server:notice","data":{"kind":"disconnect","at":<epoch ms>}}` を送る。
Pod間の `relay:migrate` と `POST /realtime/v1/instances/{id}/handoff` は内部の口で、クライアントとbackendの契約には含めない。
管理APIの作成・チケット発行・終了は任意の `?gen=&epoch=` を受け、ownerの今の世代と違えば409（今のownerを付ける）にする。
期限は入室時に検証する。既存接続の継続中にSNSの権限変更を即時反映する機能はない。

## フレームと順序

- 送信: `{event, data?, id?}`。`id` はリクエストごとに一意な100文字以内の文字列。
- 応答: `{replyTo, data}`。join/createと共有状態の操作（`state:get`・`state:update`）は応答必須。patch/delete/leaveもIDがあれば応答する。
- 通知: `{event, data?}`。失敗はリクエストIDがあれば `{success:false,error}`、なければ `error` 通知。
- 入室応答 → `users:update` → `world:snapshot` → 以降の更新、の順番で同じ接続へ送る。
- 同一インスタンスの状態変更と送信キューへの追加を直列化する。ネットワーク書き込みは接続ごとに独立。
- エンティティ作成の応答は作成者へ、created/patch/deleteの通知は他の参加者へ送る（作成者は楽観的更新）。
- 輸送は通常のWebSocket。Socket.IOクライアントでは接続できない。

## 更新と再接続

カーソル・ephemeralは古い情報を破棄できる。各接続のキューは256フレームで、揮発通知は満杯時に破棄。
確定状態の通知を積めない接続は切断し、再接続時のスナップショットで復元する。
クライアントもbufferedAmountが64KiBを超えると揮発送信を止める。

操作の自動再送・オフラインキュー・重複排除は行わない。タイムアウトしたcreate等は結果不明であり、
同じ操作を自動再実行せず再接続のスナップショットで確認する。request IDは応答の対応付けに使う。
再接続では参加チケットを取り直し、最新のローカル位置・ステータスでjoinする。

自動接続は1回の復旧につき最大6回（初回を含む）・30秒で終了する。HTTPが応答しない場合も
30秒で中断し、参加失敗を一度だけ返す。接続が10秒以上安定した後に次の復旧の上限をリセットする。
短時間の入室・切断を繰り返しても上限はリセットしない。退出・ページ離脱では待機中のHTTPと再試行を中断する。
一時的な通信エラーは再試行中として表示し、認可拒否・プロトコル不一致・上限到達だけを確定した失敗にする。
単体モードでは失敗画面に留まり、本人の「再試行する」操作で再開する（ルートへの自動移動で同じ部屋へ戻さない）。

`world:join` の失敗応答には復旧可能な場合だけ `code` を付ける。
`ticket_invalid` は失効・署名鍵の変更（単体モードの再起動・管理トークンの変更）等でチケットを検証できない場合で、同じ復旧中に1回だけ取り直す。
`ticket_invalid` は部屋の世代の不一致（チケットの発行後に owner が交代した）でも返す。
`instance_unavailable` はチケット発行後に部屋が消えた・owner が自己停止した場合で、上記の接続上限内でチケットを取り直す。
認可・パスワード・満員等の拒否は再試行しない。

切断後15秒は参加者とロックを保持する。同じIDで戻れば復帰し、期限後にロック解除と退出通知を行う。
明示退出は即時処理。同一ユーザーが別接続から入ると旧接続へ `session:replaced` を通知する。
1ユーザー1接続を保証するのは、同じ owner のGoプロセスが持つ部屋の間だけ（別のPodの部屋には通知しない）。
`instance:closing` はインスタンスの終了（リーダーの削除・空室の掃除）でのみ送る。Goプロセスの停止・owner の自己停止
（リースを延長できない・世代が変わった）では送らずに切断し、
クライアントは再接続して部屋を作り直す（SNSは部屋が無いと観測してから猶予を数えるので、その間に戻れば消えない）。

## 操作の制約

- クライアントはownerId/idを偽装できない。所有者は入室済み参加者IDから決める。
- core:*の更新・作成・削除を拒否する。ワールド初期配置でのみ作成可能。
- 他人のロックは変更できない。ロック取得時はサーバーが参加者IDを設定する。
- ownerIdがあるエンティティの削除は所有者のみ。共有データはロックされていなければ参加者が編集できる。
- エンティティのdata/transformはトップレベルのキーをマージする。
- 共有状態（`state:*`）はキーごとのrevisionによる比較と交換。値は解釈しないJSONで、サーバーは `revision`（+1）・`updatedAt`（書き込みを受けたサーバー時刻のms）・`updatedBy` を付ける。
  `expectedRevision`（無いキーは0）が一致しなければ書かずに `code: "conflict"` と今の `entry` を返す。成功した変更は書いた本人以外へ `state:changed` で配る（本人へは応答で返す）。
  キーの名前空間と値の意味（メディアの再生位置など）はHostが決める。入室時のスナップショットには含めないので、必要なキーを `state:get` で取る。
- 受信70KiB、エンティティ64KiB、ephemeral32KiB、240イベント/秒/接続が上限。
- インスタンス最大1000、部屋の参加者最大1000、エンティティ10000、共有状態はキー1000・キー512バイト・値32KiB（詰めたJSON）・合計4MiB。


reaper の DELETE は、観測した `gen`・`epoch` を付ける。409 の別世代へ削除を送り直さない。
観測時に部屋が不在なら `absent=true`（`gen`・`epoch` と同時指定不可）を付け、owner が現れていれば 409 にする。
終了時の token 照合・retired の設定・割り当てと在席の削除は Directory の原子的な操作で行い、Redis 障害時は 503 で DB の行を残す。
